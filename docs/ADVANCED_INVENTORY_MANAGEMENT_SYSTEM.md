**Capabilities:**

**Risk Factors Analyzed:**

1. **Demand Forecast Accuracy**: Higher uncertainty = higher risk
2. **Lead Time Variability**: Unreliable suppliers increase stockout risk
3. **Current Stock Level**: Days of supply remaining
4. **Seasonal Trends**: Peak season amplifies risk
5. **Supplier Reliability**: Historical on-time delivery rate
6. **Safety Stock Buffer**: Adequacy of buffer inventory
7. **Recent Sales Velocity**: Acceleration or deceleration trends
8. **Product Lifecycle Stage**: Introduction, growth, maturity, decline
9. **Historical Stockout Frequency**: Past performance indicator
10. **Market Demand Signals**: External market indicators

**Risk Scoring Algorithm:**

**Stockout Risk (0-100):**

```
Stockout Risk = (
  (1 - Forecast Confidence) * 0.30 +
  Lead Time Variability * 0.20 +
  (1 - Days Supply / Target Days) * 0.25 +
  Demand Volatility * 0.15 +
  (1 - Supplier Reliability) * 0.10
) * 100
```

**Overstock Risk (0-100):**

```
Overstock Risk = (
  (Days Supply / Target Days - 1) * 0.40 +
  Demand Decline Rate * 0.30 +
  Product Age / Max Age * 0.20 +
  Carrying Cost Impact * 0.10
) * 100
```

**Alert Severity Levels:**

- **CRITICAL (90-100)**: Immediate action required within 4 hours
  - Examples: Imminent stockout, critical environmental violation
  - Notification: PagerDuty + SMS + Email + Slack

- **HIGH (70-89)**: Action required within 24 hours
  - Examples: High stockout risk, significant overstock, device malfunction
  - Notification: Email + Slack + In-app
  - Escalation: To management if not acknowledged in 2 hours
  - SLA: Response within 24 hours, resolution within 72 hours

- **MEDIUM (50-69)**: Review within 3 days
  - Examples: Moderate risk, trending concerns, minor deviations
  - Notification: Email + In-app
  - Escalation: None unless unresolved for 7 days
  - SLA: Response within 3 days, resolution within 2 weeks

- **LOW (30-49)**: Monitor, no immediate action
  - Examples: Low risk, informational alerts, routine maintenance
  - Notification: In-app dashboard only
  - Escalation: None
  - SLA: Review during regular optimization cycles

### Data Flow Diagrams

**Forecast Generation Flow:**

```
User → Request Forecast → API Gateway → Forecast Service
                                             ↓
                        Retrieve Historical Data (Prisma)
                                             ↓
                        Calculate Ensemble Forecast
                        (SMA + EMA + Linear + Seasonal)
                                             ↓
                        Calculate Confidence Intervals
                                             ↓
                        Generate Intelligence
                        (Risk Scores, Recommendations)
                                             ↓
                        Store Forecast (Database)
                                             ↓
                        Return Results → User Dashboard
```

**Autonomous Reorder Flow:**

```
Scheduled Job (Cron) → Autonomous Service
                              ↓
            Scan All Products Below Reorder Point
                              ↓
            For Each Product:
            ├─ Get Forecast Demand
            ├─ Get Current Stock
            ├─ Get Lead Time
            ├─ Calculate Optimal Order Qty
            └─ Calculate Confidence Score
                              ↓
                    Confidence >= 80%?
                    ├─ YES → Auto-Create PO
                    │         ↓
                    │    Update Database
                    │         ↓
                    │    Notify Supplier API
                    │         ↓
                    │    Log Decision
                    │
                    └─ NO → Queue for Manual Review
                              ↓
                        Send Alert to Procurement Team
```

**IoT Data Flow:**

```
IoT Device → MQTT Broker → Edge Processing (<10ms)
                                  ↓
                        Validate Reading
                                  ↓
                        Store Time-Series Data
                                  ↓
                        Compare vs System Record
                                  ↓
                    Discrepancy > Threshold?
                    ├─ YES → Generate Alert
                    │         ↓
                    │    Update Digital Twin
                    │         ↓
                    │    Create Adjustment Record
                    │         ↓
                    │    Notify Operations Team
                    │
                    └─ NO → Update Digital Twin (Sync)
```

### Error Handling

**Standard Error Response Format:**

```json
{
  "success": false,
  "error": {
    "code": "FORECAST_GENERATION_FAILED",
    "message": "Failed to generate forecast due to insufficient historical data",
    "details": {
      "productId": "prod_123",
      "minimumDataPoints": 30,
      "availableDataPoints": 15
    },
    "timestamp": "2026-01-04T10:30:00Z"
  }
}
```

**Error Codes:**

- `INSUFFICIENT_DATA` (400): Not enough historical data
- `INVALID_CONFIDENCE` (400): Confidence score below threshold
- `DEVICE_OFFLINE` (503): IoT device not responding
- `FORECAST_EXPIRED` (410): Forecast data too old
- `RATE_LIMIT_EXCEEDED` (429): Too many requests
- `UNAUTHORIZED` (401): Authentication required
- `FORBIDDEN` (403): Insufficient permissions
- `NOT_FOUND` (404): Resource not found
- `INTERNAL_ERROR` (500): Server error

**Retry Strategy:**

- Transient errors (503, 429): Exponential backoff (1s, 2s, 4s, 8s)
- Client errors (400, 401, 403, 404): Do not retry
- Server errors (500): Retry up to 3 times with 5s delay

## Core Features Deep Dive

### Advanced Forecasting Engine

**Ensemble Model Architecture:**

The forecasting engine combines four proven algorithms to deliver industry-leading accuracy:

1. **Simple Moving Average (SMA)**
   - Best for: Stable demand patterns
   - Weight: 15% of ensemble
   - Lookback period: 30 days
   - Use case: Baseline demand calculation

2. **Exponential Moving Average (EMA)**
   - Best for: Recent trend emphasis
   - Weight: 25% of ensemble
   - Alpha value: 0.3 (configurable)
   - Use case: Short-term demand shifts

3. **Linear Regression**
   - Best for: Trending products
   - Weight: 30% of ensemble
   - Features: time, seasonality, day-of-week
   - Use case: Growth/decline detection

4. **Seasonal Decomposition**
   - Best for: Cyclical patterns
   - Weight: 30% of ensemble
   - Period detection: Automatic (7, 30, 90 days)
   - Use case: Holiday/seasonal spikes

**Confidence Scoring:**

```typescript
interface ForecastConfidence {
  score: number; // 0-100 confidence level
  factors: {
    dataQuality: number; // Historical data completeness
    consistency: number; // Pattern stability
    variance: number; // Prediction variance across models
    recency: number; // Recent data availability
  };
  interpretation: "very-high" | "high" | "moderate" | "low";
}
```

**Confidence Thresholds:**

- Very High (90-100): Minimal human review, auto-execute
- High (75-89): Standard confidence, recommend action
- Moderate (60-74): Suggest human validation
- Low (<60): Require human override

**Real-Time Adaptation:**

The system continuously learns from actual outcomes:

### Autonomous Operations Intelligence

**Decision-Making Framework:**

The autonomous system uses a multi-factor scoring algorithm:

```typescript
interface DecisionScore {
  confidence: number; // AI forecast confidence (0-100)
  riskLevel: number; // Stockout/overstock risk (0-100)
  businessImpact: number; // Revenue impact score (0-100)
  historicalSuccess: number; // Past decision success rate (0-100)
  finalScore: number; // Weighted combination
  recommendation: "auto-execute" | "suggest" | "flag-review";
}
```

**Scoring Weights:**

- Forecast Confidence: 40%
- Risk Level: 30%
- Business Impact: 20%
- Historical Success: 10%

**Auto-Execution Rules:**

```typescript
const AUTO_EXECUTE_THRESHOLDS = {
  minConfidence: 80, // Forecast must be >80% confident
  maxOrderValue: 10000, // Orders <$10K auto-execute
  minHistoricalSuccess: 85, // Past success rate >85%
  maxRiskScore: 30, // Low risk only
  requireApprovalWhen: {
    newSupplier: true,
    firstTimeProduct: true,
    unusualQuantity: true, // >200% of typical order
    criticalItem: true, // A-class items
  },
};
```

**Decision Types:**

1. **Reorder Point Triggered** (most common)
   - Current stock below safety stock + lead time demand
   - Auto-calculate Economic Order Quantity (EOQ)
   - Select preferred supplier based on price/lead time
   - Generate PO draft and execute if confidence >80%

2. **Predictive Reorder** (advanced)
   - Forecast predicts stockout in 14-30 days
   - Order placed before critical threshold
   - Prevents emergency orders and expedited shipping
   - Typical confidence requirement: 85%+

3. **Inter-Warehouse Transfer**
   - Detect imbalance: Warehouse A overstock, Warehouse B understocked
   - Calculate transfer cost vs reorder cost
   - Execute if transfer saves >$500
   - Auto-route shipment via TMS integration

4. **IoT-Triggered Adjustment**
   - RFID count differs from system count by >5%
   - Weight sensor detects discrepancy
   - Environmental alert triggers product quarantine
   - Immediate stock adjustment with audit trail

**Approval Workflow:**

For decisions requiring human approval:

- Notification sent to appropriate role (Manager/Director)
- One-click approve/reject in dashboard
- SLA: 4-hour response for standard, 1-hour for critical
- Auto-escalation if no response within SLA
- Full decision context provided (forecast, risk, impact, recommendation)

**Device Ecosystem:**

The system integrates with multiple IoT device types:

1. **RFID Readers**
   - Technology: UHF Gen 2, ISO 18000-63
   - Read rate: 1,000+ tags/second
   - Accuracy: 95%+ in ideal conditions, 92%+ in warehouse environment

   - Applications: Quantity verification, theft detection, consumption monitoring

3. **Environmental Sensors**
   - Temperature: -40°C to +85°C (±0.3°C accuracy)
   - Humidity: 0-100% RH (±2% accuracy)
   - Pressure: 300-1100 hPa (±0.5 hPa accuracy)
   - Gas detection: CO2, O2, volatile organics
   - Applications: Cold chain compliance, pharmaceutical storage, hazmat monitoring

4. **Barcode Scanners**
   - Supports: 1D, 2D, QR codes
   - Scan rate: 60+ scans/second
   - Integration: Bluetooth, USB, Wi-Fi
   - Applications: Manual verification, spot checks, cycle counts

**Digital Twin Architecture:**

```typescript
interface DigitalTwinState {
  physicalInventory: {
    lastRFIDScan: Date;
    tagCount: number;

  };
  systemInventory: {
    quantity: number;
    lastUpdated: Date;
    source: "manual" | "transaction" | "iot";
  };
  syncStatus: {
    variance: number; // Difference between physical & system
    variancePercent: number; // As percentage
    syncConfidence: number; // 0-100 confidence in accuracy
    requiresReconciliation: boolean;
    lastSync: Date;
  };
  environmentalConditions: {
    temperature: number;
    humidity: number;

    alerts: Alert[];
  };

```

**Synchronization Rules:**

- **Variance <2%**: Automatic acceptance, update system to match physical
- **Variance 2-5%**: Flag for cycle count during next scheduled count
- **Variance 5-10%**: Trigger unscheduled cycle count within 24 hours
- **Variance >10%**: Immediate investigation, freeze transactions until resolved

**Edge Processing:**

Critical IoT data is processed at the edge for <10ms latency:

- Tag deduplication (prevent double-counting)
- Read quality filtering (signal strength, read count)
- Anomaly detection (unexpected tags, missing expected tags)
- Local alerting (critical alerts don't wait for cloud)

**Data Flow:**

```

                                        ↓

                                        ↓
                                  Notification Service
```

### ABC Velocity Classification System

**Classification Algorithm:**

Products are scored on three dimensions:

1. **Revenue Contribution** (40% weight)

   ```
   Score = (Product Annual Revenue / Total Warehouse Revenue) × 100
   ```

2. **Turnover Velocity** (40% weight)

   ```
   Velocity = (Units Sold per Month / Average On-Hand Inventory)
   Score = Normalized to 0-100 scale
   ```

3. **Strategic Importance** (20% weight)
   - Customer commitments: +20 points
   - Supplier exclusivity: +15 points
   - Market differentiation: +10 points
   - Regulatory requirements: +5 points

**Class Thresholds:**

- **Class A** (Top 20% by score): 80-100 points
  - 80% of revenue, 20% of SKUs
  - High value, high velocity
  - Daily cycle counts
  - 99.9% service level target
  - Safety stock: 14-21 days

- **Class B** (Next 30%): 60-79 points
  - 15% of revenue, 30% of SKUs
  - Moderate value, moderate velocity
  - Weekly cycle counts
  - 98% service level target
  - Safety stock: 7-14 days

- **Class C** (Next 40%): 40-59 points
  - 4% of revenue, 40% of SKUs
  - Lower value, lower velocity
  - Monthly cycle counts
  - 95% service level target
  - Safety stock: 3-7 days

- **Class D** (Bottom 10%): 0-39 points
  - <1% of revenue, 10% of SKUs
  - Slow movers, obsolescence candidates
  - Quarterly cycle counts
  - 90% service level target
  - Minimal safety stock (0-3 days)

**Dynamic Reclassification:**

- **Frequency**: Monthly automatic recalculation
- **Triggers**: Significant demand change (>50%), new product launches, seasonal shifts
- **Notification**: Stakeholders notified of class changes
- **Policy Updates**: Automated adjustment of safety stock, count frequency, reorder points

```typescript
async function getRates(shipment: Shipment): Promise<CarrierRate[]> {
  const carriers = ["fedex", "ups", "usps"];

  const ratePromises = carriers.map((carrier) =>
    getCarrierRate(carrier, shipment),
  );

  const rates = await Promise.allSettled(ratePromises);

  return rates
    .filter((r) => r.status === "fulfilled")
    .map((r) => r.value)
    .sort((a, b) => {
      // Smart sorting: balance cost vs speed
      const aScore = a.cost * 0.7 + a.transitDays * 10 * 0.3;
      const bScore = b.cost * 0.7 + b.transitDays * 10 * 0.3;
      return aScore - bScore;
    });
}
```

```typescript
// Shopify inventory sync
async function syncShopifyInventory(products: InventoryItem[]) {
  const shopify = new Shopify({
    shopName: process.env.SHOPIFY_SHOP,
    accessToken: process.env.SHOPIFY_ACCESS_TOKEN,
  });

  for (const product of products) {
    // Get current Shopify inventory
    const variant = await shopify.productVariant.get(product.shopifyVariantId);

    // Calculate available to sell (ATP)
    const atp = product.quantity - product.allocated - product.safetyStock;

    // Only sync if difference > 5 units (avoid constant updates)
    if (Math.abs(variant.inventory_quantity - atp) > 5) {
      await shopify.inventoryLevel.set({
        location_id: product.shopifyLocationId,
        inventory_item_id: variant.inventory_item_id,
        available: Math.max(0, atp), // Never show negative
      });

      console.log(
        `Synced ${product.sku}: ${variant.inventory_quantity} → ${atp}`,
      );
    }
  }
}
```

### High Availability Architecture

**Multi-Region Deployment:**

```
Primary Region (us-east-1)        Secondary Region (us-west-2)
─────────────────────────         ────────────────────────────
│ Load Balancer                   │ Load Balancer
│   ↓                              │   ↓
│ App Servers (3x)                │ App Servers (3x) [Standby]
│   ↓                              │   ↓
│ PostgreSQL Primary              │ PostgreSQL Replica (Read)
│   ↓                              │   ↑
│ Redis Primary                   │ Redis Replica
│                                  │
└─────── Async Replication ───────┘

DNS Failover: Route 53 Health Checks
Failover Time: <2 minutes (automatic)
```

**Failure Scenarios & Response:**

1. **Application Server Failure**
   - Detection: Health check fails (3 consecutive checks)
   - Response: Load balancer removes from pool
   - Recovery: Auto-scaling launches replacement
   - Impact: Zero (N+1 redundancy)
   - Time: <2 minutes

2. **Database Primary Failure**
   - Detection: PostgreSQL monitoring alert
   - Response: Automatic failover to replica (Patroni)
   - Recovery: Replica promoted to primary
   - Impact: <5 minutes of read-only mode
   - Time: <15 minutes total

3. **Region Failure**
   - Detection: Multi-check failure (API + DB + network)
   - Response: DNS failover to secondary region
   - Recovery: Secondary promoted to primary
   - Impact: <15 minutes downtime
   - Time: <30 minutes total

4. **Complete Infrastructure Failure**
   - Detection: All regions unreachable
   - Response: Activate disaster recovery runbook
   - Recovery: Restore from backup to new infrastructure
   - Impact: 1-4 hours downtime (depending on tier)
   - Time: As per RTO commitment

### Disaster Recovery Runbook

**Phase 1: Assessment (0-5 minutes)**

1. Confirm disaster scenario (not false alarm)
2. Notify incident commander
3. Activate war room (Zoom + Slack #incident-response)
4. Assess scope: Single service, region, or total failure

**Phase 2: Communication (5-15 minutes)**

1. Update status page (status.flowstock.com)
2. Send customer email alerts (affected customers only)
3. Post to social media (Twitter, LinkedIn)
4. Notify key stakeholders (CSMs, Sales, Support)

**Phase 3: Recovery (15 minutes - 4 hours)**

**Scenario A: Database Failure**

```bash
# 1. Promote replica to primary
patroni switchover --master postgres-primary --candidate postgres-replica-1

# 2. Update connection strings
kubectl set env deployment/flowstock DATABASE_URL=${NEW_PRIMARY_URL}

# 3. Verify application connectivity
curl https://api.flowstock.com/health
```

**Scenario B: Region Failure**

```bash
# 1. Update DNS to secondary region
aws route53 change-resource-record-sets \
  --hosted-zone-id Z123456 \
  --change-batch file://failover-to-west.json

# 2. Scale up secondary region capacity
kubectl scale deployment/flowstock --replicas=10 -n production

# 3. Promote secondary database to accept writes
psql -h postgres-west -c "SELECT pg_promote();"

# 4. Verify traffic routing
curl -I https://api.flowstock.com
```

**Scenario C: Total Failure (Restore from Backup)**

```bash
# 1. Provision new infrastructure
terraform apply -var="environment=dr-recovery"

# 2. Restore database from S3
aws s3 cp s3://flowstock-backups/daily/latest.dump /tmp/
pg_restore -d flowstock_recovery /tmp/latest.dump

# 3. Deploy application
kubectl apply -f k8s/production/

# 4. Update DNS
# (Manual approval required for production DNS change)

# 5. Smoke test critical paths
./smoke_tests.sh https://recovery.flowstock.com
```

**Phase 4: Validation (Post-Recovery)**

1. Verify all services healthy
2. Check data integrity (row counts, checksums)
3. Test critical user flows (login, forecast, decisions)
4. Monitor error rates (should be <0.1%)
5. Confirm customer can access system

**Phase 5: Post-Mortem (Within 48 hours)**

1. Write incident report (RCA - Root Cause Analysis)

3. Identify contributing factors
4. Define action items to prevent recurrence

```typescript
// migration/import-inventory.ts
import { PrismaClient } from "@prisma/client";
import { parse } from "csv-parse/sync";
import fs from "fs";

const prisma = new PrismaClient();

async function importInventory(csvFilePath: string) {
  const fileContent = fs.readFileSync(csvFilePath, "utf-8");
  const records = parse(fileContent, {
    columns: true,
    skip_empty_lines: true,
  });

  console.log(`Importing ${records.length} products...`);

  let imported = 0;
  let failed = 0;

  for (const record of records) {
    try {
      await prisma.inventoryItem.upsert({
        where: { sku: record.SKU },
        update: {
          name: record.NAME,
          quantity: parseInt(record.QUANTITY),
          allocated: parseInt(record.ALLOCATED || "0"),
          costPrice: parseFloat(record.COST),
          sellingPrice: parseFloat(record.PRICE),
          weight: parseFloat(record.WEIGHT || "0"),
          weightUnit: record.WEIGHT_UNIT || "lbs",
          location: record.LOCATION,
          velocityClass: mapABCCode(record.ABC_CODE),
        },
        create: {
          organizationId: process.env.ORGANIZATION_ID!,
          sku: record.SKU,
          name: record.NAME,
          quantity: parseInt(record.QUANTITY),
          allocated: parseInt(record.ALLOCATED || "0"),
          costPrice: parseFloat(record.COST),
          sellingPrice: parseFloat(record.PRICE),
          weight: parseFloat(record.WEIGHT || "0"),
          weightUnit: record.WEIGHT_UNIT || "lbs",
          location: record.LOCATION,
          velocityClass: mapABCCode(record.ABC_CODE),
        },
      });

      imported++;

      if (imported % 100 === 0) {
        console.log(`Progress: ${imported}/${records.length}`);
      }
    } catch (error) {
      console.error(`Failed to import ${record.SKU}:`, error);
      failed++;
    }
  }

  console.log(`\nImport complete!`);
  console.log(`Imported: ${imported}`);
  console.log(`Failed: ${failed}`);
}

function mapABCCode(code: string): string {
  const mapping: Record<string, string> = {
    A: "A",
    B: "B",
    C: "C",
    D: "D",
    F: "D", // Map F to D (slow movers)
    "": "C", // Default to C if missing
  };
  return mapping[code] || "C";
}
```

### Tenant Isolation

**Data Isolation Strategy:**

1. **Database-Level Isolation** (Recommended for Enterprise)
   - Each tenant gets dedicated PostgreSQL schema
   - Complete data separation
   - Independent backup/restore

```sql
-- Create tenant-specific schema
CREATE SCHEMA tenant_acme_corp;

SET search_path TO tenant_acme_corp;
```

2. **Row-Level Security** (Standard/Pro tiers)
   - Shared tables with `organizationId` column
   - PostgreSQL RLS policies enforce isolation
   - More cost-effective for smaller tenants

```sql
-- Enable RLS on table
ALTER TABLE inventory_items ENABLE ROW LEVEL SECURITY;

-- Policy: Users can only see their org's data
CREATE POLICY tenant_isolation ON inventory_items
  USING (organization_id = current_setting('app.current_organization_id')::text);
```

   - Every query includes `WHERE organizationId = ?`
   - Enforced at ORM level (Prisma middleware)
